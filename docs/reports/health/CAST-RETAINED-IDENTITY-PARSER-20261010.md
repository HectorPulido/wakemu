# Repeated retained-effect protobuf parsing during casts

The 06:54 UTC live incident included caster 4 request `20e3e76b55634b978446548044cbc534` taking approximately 8,873 ms. The continuous capture preserved under `.runtime/local/diagnostics/slow-combat-20261010-0654/` shows repeated event replay building complete retained-effect views. The sampled chain is `NativeEventReplay.__call__` -> `retention.view` -> `NativeRetainedEffectView.__init__` -> `_identity_fields`. The live capture audit found 129 of 225 cast-window samples in event replay, including repeated immutable identity-field parsing. These samples do not imply that all cast latency belongs to parsing.

The common parser now reuses validated immutable protobuf facts. The cache key includes exact payload bytes, selected integer fields and whether embedded messages are requested. Return dictionaries remain private. Ownership, current retained population, manager identity and other live-view checks still execute on every view. Altered bytes produce a different key. Malformed payloads and duplicate fields retain existing error behavior, including caller-visible partial message updates. Mutable or oversized inputs use the uncached parser.

The cache holds at most 512 entries, each with at most 4,096 source bytes and 16 selected integer fields. Source bytes are bounded to 2 MiB, extracted message bytes to 2 MiB, with additional bounded tuple/integer/key object overhead. This is a process-local pure-data cache, independent of fight lifetime.

Validation: four focused regressions pass, covering reuse, independent return containers, changed bytes, field/message mode separation, malformed and duplicate handling, prepopulated messages, mutable/large bypass and LRU retention. A synthetic 100,000-repeat representative payload benchmark measured 0.401 s uncached versus 0.081 s cached (4.96x). This is not a claim about full-cast or live response time. Broader retained/event replay validation is delegated before deployment.
