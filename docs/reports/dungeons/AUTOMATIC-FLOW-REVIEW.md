# Automatic reconstruction of natural dungeon flow

The automatic extraction method now separates three evidence layers: exact native transports, physical gate candidates, and client scenario references. It runs across the installed native dungeon catalog. It does **not** yet reconstruct certified official room order or victory-to-door unlock rules. No service, running dungeon or combat behavior was changed by this research.

## Outputs and reproducibility

- [Dungeon inventory](INVENTORY.md), [per-dungeon detail](DETAILS.md) and [structured identity/roster/object evidence](inventory.json).
- [Native geometry analysis](GEOMETRY-TOPOLOGY.md), [topology data](topology.json), generated by `server/tools/extract_dungeon_topology.py`.
- [Focused Tofu directed-path and gate proof](TOFU-NATIVE-FLOW.md), generated by `ExportNativeExplorationMap.java` and `extract_native_door_flow.py`; see its companion JSON for paths and confidence.
- [Native door parameters and Lua references](native-script-flow.json), generated by `sniffer/java/ExportDungeonDoorParameters.java` and `server/tools/extract_dungeon_script_flow.py`.
- [Public-version crosscheck](PUBLIC-VERSION-CROSSCHECK.md): keep the client version distinct from modern room layouts.

Native catalog documents were obtained in an explicit PostgreSQL READ ONLY transaction. The release and document hashes are pinned in the private snapshot manifest. Lua is read directly from the installed `client/contents/scripts/scripts.jar`; scripts are never executed. No numeric Lua filename is treated as a map ID without an independent native link.

```sh
mkdir -p .runtime/local/dungeon-door-extractor-classes
javac -proc:none -cp 'client/lib/*' \
  -d .runtime/local/dungeon-door-extractor-classes \
  sniffer/java/ExportDungeonDoorParameters.java
java -cp '.runtime/local/dungeon-door-extractor-classes:client/lib/*' \
  ExportDungeonDoorParameters \
  .runtime/local/methodwakfu-dungeons/inventory-native-snapshot/native-map-objects.json \
  .runtime/local/methodwakfu-dungeons/inventory-native-snapshot/door-parameters.json
python3 server/tools/extract_dungeon_script_flow.py
```

The geometry extractor has its own invocation and limitations in its linked report. These commands produce research artifacts only; no configuration is installed.

## What can be recovered automatically

| Layer | Evidence recovered | What it establishes | What it cannot establish |
| --- | --- | --- | --- |
| Native transports | Source object IDs, destination coordinates, map, native criteria and item requirements | Exact authored transport edges | Which encounter unlocks a transport, or whether the current server supports it |
| Door objects | Native decoder state, visibility/usability flags, position and raw parameters | Actual native Door objects and baseline state | Boss/encounter dependencies absent from the parameters |
| Geometry | Native movement graph with door cells present and removed | Candidate physical region separators | Scripted stairs, directed terrain edges, encounter order or official unlock authority |
| Lua | Typed `InteractiveElement.method(object_id, ...)` calls and scenario event comments | Authored presentation references to exact object IDs | Server-side conditions, encounter ownership or authoritative unlock events |

The geometry pass extracted **151 maps**, including **98 maps with Door objects**. It found **211 separator candidates across 87 maps**, from 434 native dungeon Door objects. A separator candidate is a diagnostic graph cut, **not a certified room transition**. A dungeon definition and a unique map are distinct counting units.

The native Door decoder exported **818 doors globally**. **816 have empty parameters**; the remaining two parameters are `927` and `false;false`. Bytecode for `bEE.Door -> bBk` shows that `bBk.dSG` interprets an interaction-right enum (`ALL`/`GUILD`) and at most two booleans. It does not decode monster IDs, room numbers, quest IDs or victory conditions. Native state changes are therefore an important client contract, but they are not an encounter controller definition.

The Lua scanner inspected **27,263 scripts** and recovered typed references to **12 dungeon object IDs**, all generic activable elements rather than native Door objects. For example, `scenario/2205.lua` calls `InteractiveElement.setAnimation(33343, ...)` from its `openDoor` helper. Object 33343 belongs to Fosse du Tourmenteur and is `GenericActivableInteractiveElement`; a visually named door need not use native type `Door`. These calls control animations and cannot themselves certify collision changes or combat completion. **166 scenario files** contain candidate fight-end/death/door-opening event comments, but their map and server event bindings still need extraction. No official victory-to-door dependency has yet been recovered.

## Tofullero: concrete evidence and remaining gap

Native definition 27 uses map 1087. The three native doors are:

| Door | Position | Baseline | Geometric result |
| --- | --- | --- | --- |
| 26873 | `(13,-38,-8)` | State 1, hidden, unusable; empty parameters | Not a separator under the single-cell hypothesis |
| 26874 | `(23,-35,-8)` | State 1, visible, unusable; empty parameters | Separates two substantial regions |
| 26875 | `(39,-26,-12)` | State 1, visible, unusable; empty parameters | Separates the next pair of substantial regions |

Native collision bytecode confirms that a normal Door uses its exact `(x,y,z)` cell (or the column when there is only one surface), rather than a guessed multi-cell model footprint. `Re.beu()` requires both the collision flag and visibility, so hidden door 26873 cannot be a blocking gate in its baseline. Blocking all three door cells in the diagnostic pass yields substantial components of 182, 207 and 230 cells. Doors 26874 and 26875 form a useful candidate three-region chain. The initial combat-profile graph put native entry `(14,-25,0)` in a separate 37-cell component. Subsequent native client analysis resolved this: normal player exploration uses movement profile `(6,0,4)`, while the earlier combat export used `(3,0,2)` and rejected the height-four stair. The exploration graph connects entry to the first region and then doors 26874 and 26875 connect the next regions. See [Tofullero controller review](TOFULLERO-CONTROLLER-REVIEW.md). Keep combat geometry unchanged; natural room composition and official unlock callbacks are still unverified.

There are **zero literal references** to door IDs 26873, 26874 or 26875 in the installed Lua archive. `scenario/-1087.lua` is a resource challenge and is not a proven map-1087 controller. Matching a script filename to a map number would produce a false association.

The prior local policy hides native travel objects and substitutes automatic travel. That approach neither opens physical Door collision nor resolves the disconnected entry. Restoring natural progression requires solving both the geometry connection and object-state publication, not just unhiding teleports.

## Next general extraction step

1. Complete the **native directed movement contract**, retaining altitude, boundary flags and special movement/trigger links. Door anchor-cell collision is already supported by native bytecode (`bEG -> VD.a(x,y,z,blocked)`); non-Door objects may have another contract. Apply baseline visibility before interpreting blocking. Explain every native entry's connection to encounter-capable regions before creating a room sequence.
2. Export native event/scenario definitions and their references to map/instance, object activation, fight end, monster group and state-change actions. Link `scenario/<id>.lua` through those IDs, rather than filename coincidence. Preserve absent server-only actions explicitly; empty Lua handlers are not a complete controller.
3. Build a typed graph with nodes for native object, region, encounter and scenario event. Keep transport edges, physical candidate edges, client animation edges and authoritative unlock edges separate. Only authoritative dependencies can order fights; geometry alone may establish an undirected corridor chain.
4. Compare the resulting chain to reviewed per-room guide evidence for the installed version. Reject unsupported first-boss placement and generated pool padding. A species pool is never an encounter composition.
5. Export a draft per-instance door policy with source hashes and confidence. Activate only after automatic invariants pass: reachable native entrance, connected party-capable encounter area, no cross-room movement through closed gates, one unlock after durable victory, no unlock after defeat/withdrawal, correct reconnect restoration and independent parties. Where authority remains absent, label a deliberate local progression policy rather than presenting an inferred sequence as official.

This pipeline avoids researching each dungeon manually first. It automatically narrows unresolved cases to missing native movement or controller evidence. The current artifacts supply its initial evidence inputs; they are not yet sufficient to install a correct natural progression policy for every dungeon.

The user's request to open dungeon entrances regardless of missions is a separate entrance-access change. It should not erase interior door dependencies or declare quest NPCs, secrets, chests or bosses implemented.
