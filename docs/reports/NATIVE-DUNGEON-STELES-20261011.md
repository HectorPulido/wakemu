# Native dungeon steles: configurable server implementation

Status: source staged, native interface oracle passed, final binding/pure/PostgreSQL gate 24/24 passed. Not deployed. All 115 selected native states pass actual first-active-turn installation; representative native trigger, checkpoint and replay tests pass. Dispatcher integration is implemented and automatically verified; deployment and manual acceptance remain pending. This does not establish every monster-specific stele mechanic end to end.

## Design and scope

The user authorized a server approximation based on [Method Wakfu's stele guide](https://methodwakfu.com/pvm/les-steles-de-donjons/). The guide establishes leader activation in the boss room, competitive eligibility, cumulative difficulty/options, activation costs and additional selected reward eligibility. Its November 2025 rules are design context, not evidence that this installed version uses the same resource IDs or complete monthly rotation.

Migration 133 imports the installed definitions used by all 36 existing stele placements (35 definitions, IDs 6–40). Native costs, difficulty weights/state IDs, tier weights, free option counts, reward IDs/item references and quantities are retained. The server uses a fixed configurable rotation: each tier exposes the first native `dynamic_rewards_count` rewards ordered by native order then ID. SQL configuration can change that subset. Monthly official rotation is not reproduced.

Default eligibility requires competitive mode, minimum Stasis 1. These placements belong to the native sublimation stele family; three-player/intervention steles are not invented. The configured activation cost is charged for each newly selected difficulty, additional selected dynamic rewards beyond native free counts use the native option cost. Paid options are cumulative for the boss attempt. Native listed quantities describe the interface; they are not unconditional grants or invented drop rates.

## Native evidence

`sniffer/java/ExportSteleDefinitions.java` loads installed aNx definitions through apw. Native bbX/flI/flK/flL/flO/flM establish field semantics: interaction category, activation criteria/cost, additional option cost, difficulty ID/weight/state ID, tier required weight/free count/static and dynamic rewards.

The native selection message csK/12686 contains `i64 stele definition ID`, `i16 difficulty count` followed by i32 difficulty IDs, then `i16 reward count` followed by i32 reward IDs. The long is not an environment object ID. Selection therefore requires a server-owned browse lease for the actual placed object. Native bDS starts its blM occupation 34 locally before sending browse action 12; action 13 closes it locally. No synthetic occupation-start packet is needed. Rejected browse requests cancel the local type-34 occupation with native12088 `(phase3,type34,character_id,empty payload)`; the installed chT generic cancellation branch calls the matching occupation cancellation, and blM removes the stele controller. `VerifySteleCancellation.java` passes the actual cyN decoder and blM type check. Selection errors preserve the editable occupation for correction/retry. Native bQt renders 13326 as editable content during occupation 34 and as preview otherwise.

Response cBd/13326 is native protobuf zG: steleId field 1, repeated reward tiers field 2, repeated enabled difficulties field 3, active field 4. Tier zC fields are tierId/staticRewards/dynamicRewards/requiredWeight. Reward zK fields are rewardId/itemId/quantity/enabled.

`sniffer/java/VerifySteleInformation.java` decoded an actual server response using the installed zG/zC/zK classes: PASS, complete tiers and both reward lists. Python packet/selection tests: 5/5 PASS.

## Ownership and persistence

`maps/dungeon_stele.py` exposes:

- `definition(store, map_id, object_id)` → read-only placed-stele classification.
- `browse(store, account_id, generation, character_id, object_id)` → native response packet list and five-minute owned browse lease.
- `close(store, account_id, generation, character_id, object_id)` → release only the matching owned browse lease.
- `activate(store, account_id, generation, character_id, body)` → inventory quantity deltas, optional wallet refresh and native response; one transaction.
- `freeze_encounter(db, instance_id, fight_id)` → immutable JSON snapshot, after dungeon encounter binding in the same transaction.
- `encounter_snapshot(db, fight_id)` → saved snapshot or None; safe when migration 133 has not been applied.

Selection verifies the live session and character ownership, active run and current final room, actual room spawn receipt/map, active generation-specific dungeon leader membership, current party leader, native object placement/range, absence of active encounter and competitive/Stasis policy. Client IDs do not establish dungeon authority.

The run lock serializes activation and fight binding. Identical selection replays return the previous state without charging twice. A failed resource/wallet operation rolls back all consumption and selection. Fight binding validates the already frozen dungeon difficulty revision, freezes selected reward allowlists, then invalidates interaction leases while preserving paid selections for the run. Reconnect/replay reads the immutable receipt; defeat/abort retries reuse the paid choices without another charge. Lowered Stasis preserves paid challenge states but excludes associated reward items from the encounter allowlist. After the first encounter, the existing difficulty policy permits only Stasis reductions: competitive-mode changes and Stasis increases are rejected. The reward projection also defensively excludes ineligible competitive selections. The additive Stasis2→1 regression passes: state8318 remains selected, eligible_rewards is false, the item allowlist is empty, defeat retry is free, and raising Stasis again is rejected.

`maps/dungeon_fight_binding.py` calls the freeze after `bind_encounter`. The reward consumer is owned by the drops agent: only native monster drop rows whose item reference occurs in `selected_stele_item_references` become eligible. A boolean never unlocks all 634 stele-dependent rows.

## Native combat state activation and verification

The installed selected difficulty definitions reference 115 distinct native states. Their effect closures contain 36 effect classes. Many roots are retained trigger groups; some states are markers consumed by monster-specific mechanics. For example, state 4020 has a first-table-turn group targeting enemies; state 8167 is a marker only. Attaching every state to every monster would duplicate global effects and cannot be claimed correct.

Native client data proves state/effect definitions, selectors, criteria and triggers; it does not include the official server's carrier assignment. Any boss-carrier policy must be explicit server configuration, retain native effect semantics, use complete fight actor authority and pass constructor/reconnect publication checks. No arbitrary replacement stats are justified by this evidence.

`maps/dungeon_stele_states.py` stages an explicit boss-carrier adaptation: the frozen final-room roster must identify exactly one actual enemy boss actor. It applies native level-1 states through the existing retained state handler **after ready(), at the first active turn, before native fight-start event 1003**. This is a server-owned activation boundary. It preserves the registered boss and its exact QI slot/topology. The complete player/NPC runtime emits actual native state packets; return value is `(private_preview, receipt, packets)`. Replays emit no packets. The receipt pins the selected encounter and complete state/effect closure SHA. Ambiguous multiple bosses reject before state publication.

Constructor placement testing qualified 113/115 states and correctly rejected 4618/6123: their immediate native maximum-resource effects require an active fight. The implementation therefore uses the proper first-active-turn boundary for every selected state; it does not weaken resource-handler guards or silently omit those states. The full 115/115-state installation gate passes at that boundary. Three representative states (4020, 8167, 8318) pass actual full-runtime installation, immutable receipt/checkpoint/replay, empty replay outbox and exact QI slot/cell/topology preservation. State 4020 passes its actual native event-1003 semantic test: exactly three maximum MP are removed from the enemy player, while the boss remains unchanged. State 4020 targets enemies of its boss carrier, reducing the player's maximum MP through native class 57; it does not reduce boss AP.

## Complete manual acceptance after deployment

For the installed stele definition 10 (native placement map 202, object 34855), the activation cost is one item 32964 per difficulty. Before the run, the authorized console command `!item 32964 10` supplies ten activation resources. Use the actual dungeon entrance and progression; teleporting to the asset map does not create a valid owned run. Other definitions use their own imported costs shown in the native panel.

1. Enter a supported dungeon with a party, as leader, in competitive mode. Advance normally to its boss room. Open the stele next to the party. Expect the native panel, the configured fixed reward options and actual native resource costs.
2. Select one difficulty and one free unlocked option. Confirm once; reopen the panel. Expect the same active difficulty/reward and exactly one resource charge. Repeating the identical confirmation must not charge again.
3. Add another difficulty and enough options to exceed the tier's free count. Expect only the additional activation/option cost. Insufficient resources must leave inventory, wallet and selection unchanged.
4. Have another party member attempt activation, move outside interaction range, and try opening a stele outside the active boss room. Expect rejection without resource consumption.
5. Start the boss fight. Confirm the same qualified selected states/tooltip and selected reward scope for all party members. Reconnect a member: the frozen encounter selection must remain identical. Changing panel selection during the encounter must fail.
6. Finish the encounter. Only selected-item native drop rows may roll under their normal native rates; a selected item is not guaranteed. Unselected stele rows must remain ineligible. Replay/reconnect must not duplicate rewards.
7. Defeat the boss attempt and retry. Reopen the stele: the previous paid choices remain selected, and resubmitting the same choices charges nothing; additional choices charge only their delta. After a paid activation, lower Stasis below the configured minimum between encounters: the boss challenge states remain frozen, while associated selected-item reward eligibility is empty. Competitive-mode changes and Stasis increases after an encounter must remain rejected by the existing difficulty policy. New browsing/activation still requires current eligibility.
8. Verify an ordinary dungeon room, world fight, duel and Rift still use their existing combat/reward behavior.
