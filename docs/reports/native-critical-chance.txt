Críticos: estadística propia, rama nativa y política de sorteo

Evidencia original: ffw.sgI es FEROCITY, PC9, base3 y límites nativos
-1000..1000. fqX.CRITICAL_CHANCE usa precisamente ffw.sgI. eVi150/168
son ganancia/pérdida de Coup Critique (%). UI bll representa su valor directo
como porcentaje, distinto del dominio crítico PC52. ProbeNativeCriticalChance
verifica PC9, enum, límites/base y UI37% en Java original.

El cliente no contiene el productor servidor del sorteo. La política local
implementada y señalada como inferencia del servidor es: chance actual PC9,
umbral limitado0..100, randint1..100 <= umbral. Un lanzamiento decide una sola
rama y esa rama se comparte entre todos los efectos y notificaciones. Chance
imposible o garantizada no sortea; no rama crítica acreditada no sortea. No se
aplica multiplicador genérico: daños/curas críticos provienen de los efectos
nativos seleccionados por la rama. Efectos CRITICALS_ONLY/NO_CRITICALS conservan
la selección existente. La estadística actual puede cambiar por equipo/estado:
no se usa un base3 supuesto cuando falta el snapshot.

API común combat_critical.choose_critical(actor,rng,mode,critical_available)
retorna CriticalDecision con bool critical y campos seguros para trazas.
Modos auto/normal/critical: los últimos dos son overrides explícitos de pruebas.
Auto rechaza snapshot desconocido, valores no integrales y fuera de límites.

Para producción se recomienda prepare_with_critical(actor,rng,prepare,...),
que incluye el primer sorteo y toda la preparación del preview en el mismo
rollback_external_rng. Callback prepare recibe critical=bool y el mismo RNG,
y retorna preview sin publicar. Si una condición/efecto posterior rechaza,
restaura estado aleatorio previo incluyendo decisión crítica. Éxito conserva
avance. Capturar estado sólo dentro del entry de hechizo no basta si el main
ya sorteó antes: sería un rollback parcial. No se requiere Redis para este RNG.
