Grupos de monstruos: Redis autoritativo y lotes SQLite

RedisGroups sustituye PersistentGroups manteniendo register, available, claim,
finish, release_session, respawn y respawn_due. Las mutaciones se confirman con
CAS en Redis antes de devolver éxito. Redis configurado e inaccesible provoca
error: no existe una transición silenciosa a SQLite.

Integración: construir con STORE, cliente redis-py, recover=True exclusivamente
al arrancar el único servidor del mundo, y lease_active(generation) que consulte
las sesiones vigentes. Invocar flush_due() desde el flusher y close() al apagar.
Intervalo predeterminado: 1200 segundos. El cliente Redis y AOF se configuran en
Compose; este módulo no inicia ni reinicia servicios.

Cada registro contiene clave mapa/instancia/grupo, miembros completos, estado,
generación, fight_id, revisión, fecha de derrota y baseline SQLite exacto.
El lote SQLite es transaccional. El checkpoint posterior conserva una mutación
Redis más reciente. Si se pierde el checkpoint tras commit, el siguiente intento
reconoce la versión ya guardada sin duplicarla. Una divergencia externa respecto
al baseline se rechaza y revierte el lote completo.

Recuperación: Redis conserva incluso grupos registrados sin flush previo.
Reservas de combates perdidos se liberan incrementando revisión; resultados con
el lease antiguo no pueden derrotar el grupo recuperado. Derrotas permanecen
hasta respawn explícito. Si Redis se vacía, SQLite solo recupera el último lote;
AOF persistente es necesario para conservar los veinte minutos pendientes.

Límites: requiere un único escritor del mundo para registros de grupos nuevos
con identidad NPC global. CAS protege reservas del mismo grupo entre workers,
pero la validación de identidad entre grupos diferentes no constituye una
transacción Redis distribuida. recover=True no debe ejecutarse en un segundo
worker activo. El adaptador de equipo todavía no forma parte de este módulo;
StateJournal proporciona su base reutilizable, no una integración terminada.

Pruebas: Redis real local con namespaces UUID aislados y SQLite temporal;
registro, recuperación, derrotas, sesión caducada, reserva entre workers,
lote a los 1200 segundos, cierre, checkpoint tardío, fallo tras commit,
conflicto SQLite y restauración desde SQLite. Sin reinicios ni conexiones oficiales.
