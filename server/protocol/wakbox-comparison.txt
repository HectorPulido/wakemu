Fecha del commit: 2017-07-03
Su README y configuración apuntan a Wakfu 1.54.0. El cliente capturado anuncia 1.93.2. La revisión se hizo sobre el código clonado; no se compiló ni se ejecutó el servidor antiguo.

Qué se conserva:
- Separación dispatcher/autenticación y servidor de mundo.
- Intercambio de versión, desafío/clave RSA, resultado de autenticación, listado de servidores, ticket y selección de personaje.
- Selección de personaje: id de 64 bits seguido por nombre con longitud de 32 bits.
- Coordenadas x/y de 32 bits y altura de 16 bits.
- Pasos de movimiento en un byte: 3 bits de dirección y 5 bits de diferencia de altura con signo. La tabla de ocho direcciones es idéntica.
- Varios contenedores de entrada al mundo siguen usando bloques con tamaños de 16/32 bits.
- Protobuf sigue presente. Tras normalizar el prefijo de paquete antiguo WakfuProto, 53 tipos pueden compararse por nombre: 36 conservan exactamente los campos comparados; 17 presentan cambios. Se compararon número, nombre, tipo, repetición/requerido, tipo referenciado y valor por defecto, no todos los enum/opciones/contratos funcionales. No se afirma compatibilidad completa por esta coincidencia.

Qué cambió:
1. Transporte. WakBox usa QTcpSocket sin TLS en los servidores revisados. Las conexiones oficiales capturadas usan TLS. En este JAR aTl.d(...) recibe la opción TLS y los intentos de conexión al mundo la activan; aBW.bYq() construye el contexto de cliente. Un servidor de prueba necesita atender ese transporte o un perfil local del cliente expresamente configurado para su transporte.
2. Cabecera. WakBox lee/escribe longitud total u16; el cliente actual usa u32. Las cabeceras pasan de 5 a 7 bytes cliente->servidor y de 4 a 6 bytes servidor->cliente. Los opcodes siguen siendo u16, pero sus valores cambiaron. No hay un desplazamiento numérico uniforme.
3. Autenticación. El servidor antiguo descifra salt+usuario+contraseña y consulta SQL. El flujo actual capturado recibe un token del launcher y manda autenticación cifrada al dispatcher. El ticket de mundo conserva str32 y añade otro str32 con identificador de máquina. Las estructuras de información de cuenta crecieron.
4. Petición de ticket. Antiguo: u32 server_id + u64 account_id. Actual cmS: i32 server_id + bool presencia + i64 opcional.
5. Movimiento. La petición actual añade i32 movement_mode antes de las coordenadas. La respuesta de actualización de posición añade el mismo tipo de campo al final. El handler antiguo leería el modo como x y quedaría desalineado.
6. Lista de personajes. La colección de blobs conserva el conteo, pero cada blob de cEk usa longitud u32 en vez de u16. Hay registros adicionales. El formato interno del personaje requiere adaptación separada.
7. Cadenas. Packet.h usa Latin-1 y a veces cuenta caracteres o reduce longitudes a u8. BV.aS del cliente actual usa UTF-8 y cuenta bytes. El chat de proximidad/comercio usa ahora longitud u16. No conviene reutilizar esos helpers antiguos sin corregirlos.
8. Datos de personaje/mundo. Los tamaños de los contenedores externos no garantizan que el contenido antiguo funcione. Builds, equipo, inventarios y recompensas incluyen campos añadidos, retirados o referencias cambiadas. Los valores de raza, objeto y mapa fijados en 2017 no están verificados para este cliente.
9. El propio proyecto es incompleto: SendCharacterEnterWorldPackets contiene TODO y partes comentadas; el handler de inicio de pelea está sin registrar en Opcodes.cpp. Su existencia no prueba que login/caminar funcionen hoy ni que combate estuviera completo.

Conclusión para un servidor local sencillo:
La arquitectura y el algoritmo de pasos sirven como referencia. Arrancar ese repositorio con nuevos opcodes no es suficiente. Un prototipo de una cuenta y un personaje puede mantener su estado en memoria y limitarse a una zona; no necesita implementar toda la base de datos, chat ni combate.

Orden concreto de fase 2:
1. Perfil local separado, dispatcher/world en loopback y transporte compatible. Usar un token ficticio aceptado solamente por el servidor del experimento. No enviar ese token al servicio oficial.
2. Implementar versión/desafío y autenticación de laboratorio, una lista de servidor y un ticket local efímero. Reproducir las estructuras actuales de cuenta, no copiar las antiguas.
3. Presentar un personaje sintético y aceptar su selección. Decodificar y construir sus bloques actuales de personaje/cuenta; evitar flags de recustom/renombrado para ese personaje.
4. Emitir la inicialización mínima de mundo: información local, posición, instancia y datos de zona necesarios. Este es el mayor pendiente: los blobs internos de personaje todavía no están totalmente interpretados.
5. Procesar opcode 13331, calcular destino y conservar posición. Emitir opcode 13530 con modo de movimiento y comprobar posición antes/después desde el cliente. Validar cambios de partición si se permite salir de una zona.

Criterio de éxito: el cliente entra con el personaje sintético en el servidor local, completa la carga y un clic produce un cambio de coordenadas confirmado. Hasta entonces no se considerará logrado login+caminar. En esta fase de análisis no se creó ni se arrancó ese servidor.
